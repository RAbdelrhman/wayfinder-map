# Canvas performance investigation, #305

Work in progress on 2026-10-22, based on `6dce3d6` after #304 merged. This is not evidence that the map's 60 fps bar is met. The ticket stays open.

The only retained source change avoids replacing the feedback marks-layer HTML when the generated markup has not changed. A board scroll reports an empty marks layout even when no feedback tool is active. Previously every report destroyed and rebuilt the same board hint. The regression test preserves the node across 60 layout messages, checks that no child-list mutations occur, and confirms that changing from the board to an option still removes the hint. Existing tests cover moving marks and feedback interaction. No controls, copy, layout, or selected prototype behavior change.

An exploratory pan trace recorded 117 main-viewer layout/layerization passes. A later trace with the retained change recorded two layouts and four layerization passes. Those traces used different zoom/scroll positions, so the counts establish a useful lead, not a matched performance verdict. A controlled comparison is still required. Some subsequent pans had no frames over 20 ms, but other runs still had rare long frames. The cause of every remaining pan stall is not established.

An expanded zoom trace caught a 44.304 ms `RendererRasterWorker` task on the GPU process. The enclosing `GPUTask` attributed the work to renderer 36564. Chromium's frame metadata maps both the open canvas and background tile previews to that renderer. This supports GPU raster work as a zoom bottleneck, but does not by itself distinguish the nested options from background preview content. Hiding the covered background app did not eliminate the stalls in exploratory runs.

Experiments were applied only to the test window or through a test-only network response override. None of the following is in the source diff:

- A transform transition on the stage worsened zoom, at about 52-56 fps with 8-11 frames over 33 ms per sequence.
- Keeping iframe layers still stalled. An unmatched screenshot crop suggested lower edge sharpness at 200%, but the crop comparison failed independent review and is not accepted sharpness evidence.
- A constant CSS zoom of 200% with a compensating outer transform worsened zoom to about 55 fps. Worst frames were 117-217 ms. It is rejected before any extents claim.
- Backface/3D layer rules, iframe content visibility, remembered frame containment, viewport containment, and hidden covered previews did not reliably eliminate the long frames.

Raw exploratory results and explicit limitations are in [the evidence JSON](../evidence/canvas-performance-305.json). Earlier samples with one-second animation-frame cadence or repeated frame timestamps were rejected. An early sampling loop could restart old callbacks between samples; affected frame counts are not acceptance evidence. Later experiments use a sample-local stop flag. A matched pan attempt also rejected repeated timestamps rather than accepting an inflated frame count.

The desktop development window ran Electron 44.4.3 with background throttling disabled for measurement, on the Intel UHD 630 through ANGLE D3D11 with GPU rasterization enabled. It loaded the shared UI from this worktree on port 4495. The localhost diagnostic server on port 4496 adds only a finite frame-timing probe to served HTML; it is generated under `dist/`, is not a source change, and exposes no privileged operation. Localhost zoom was exercised with the existing zoom buttons through T3's collaborative browser. Desktop zoom used real Ctrl+wheel. One earlier desktop test window and the localhost tab remained active during exploratory batches; they were subsequently closed to remove that confound. No installed-release performance claim is made.

Independent Opus 5.5 review round 1 found no source defect, but marked none of the four Done-when items Pass. The original page-target traces omitted the canvas renderer, so their GPU observations cannot establish the canvas's cause. The review also rejected the unmatched sharpness comparison, insufficient repeats, and canvas-only timing as evidence for a viewer-side fix. The unsupported compositor-layer comment was removed, and the moving-pin test now explicitly checks that changed positions still update.

Browser-target tracing subsequently captured both isolated renderers, including 43,666 canvas-renderer events in one zoom trace. Input markers and frame clocks from both renderers were added. Ten interleaved untraced runs per arm compared the existing implementation with a constant identity-transform variant: each arm contained 2,334 canvas frame intervals; baseline had 14 intervals over 20 ms (worst 83.6 ms), versus 13 (worst 66.6 ms) for the variant. That difference does not establish an improvement. The recurring gap followed the 50% to 33% zoom step by roughly 100–160 ms, so the 100% layer-rule crossing alone does not explain it. These are animation-frame intervals, not proof of displayed-frame delivery.

A later direct-CDP sample produced roughly one frame per second in both contexts despite reporting visible documents. The harness rejected it. It is not a valid performance result. A software-raster comparison also yielded no valid sample because app discovery/loading timed out; that timeout says nothing about the GPU backend's performance.

Fresh checks after the review changes passed: `bun run typecheck`, `bun run lint`, and `bun run test` each exited 0; 128 test files and 1,683 tests passed. Output is retained locally in `.audit/305-{typecheck,lint,test}-verified.log`. These checks cover the retained feedback DOM change, not any rejected experiment.

The user subsequently reported that the canvas feels smooth and asked to finish with the existing improvements. The deliverable therefore retains only the reviewed feedback DOM optimization and its tests. The experimental zoom and GPU settings are excluded. This user observation is useful acceptance feedback, but does not establish the original quantitative Done-when items.

A matching development-desktop pan comparison used native pointer input scheduled at 60 Hz for four seconds at both 100% and 200%. CDP round trips stretched the input schedule: maximum drift ranged from 514 to 2,393 ms between batches, so the actual input rate was lower. Three runs per zoom and arm are a flow check, not enough to establish the absence of rare stalls or a frame-rate improvement. The before arm overrides only the compiled app's cache guard to restore the old rebuild behavior. The after arm uses the source implementation. Background gallery iframes were hidden in both arms, and the real viewer was opened through a test-only origin entry fixture to avoid variable GitHub discovery latency. The before arm recorded 228–232 child-list mutations per drag; the after arm recorded none. Both renderer clocks, input schedules, state, mutation counts and first-run browser traces were saved locally. Summary numbers are in the evidence JSON. No installed-release or localhost performance claim follows from this controlled desktop check.

Before closing #305, the zoom fix must be chosen and demonstrated, every remaining pan stall must be attributed, and controlled repeated desktop/localhost runs must meet the ticket. Final 200% sharpness and scroll-extents comparisons against CSS zoom are still required, as is an independent all-Pass verdict. There is no PR or merge yet.
